# 이동·교시·급정지 복구 점검 (2026-11-16)

2026-11-16 변경: `python nero_enable.py`는 이전 `NO_SOLUTION`이나 목표 미도달 표시와 관계없이 모터 활성화를 요청하고, 새 드라이버 피드백에서 모터 7개 활성화를 확인합니다. 실제 급정지는 자동 해제하지 않습니다. 모터가 켜져도 남아 있는 경로 오류는 별도로 표시합니다. 이동 프로그램은 남아 있는 경로 거부 표시만으로는 이동을 막지 않습니다(아래 "전자 급정지 정책" 참고). enable 실패만으로 자동 급정지/reset/disable을 보내지 않습니다.

## 관절 범위 밖에서 enable / disable (2026-11-17)

`python nero_disable.py`는 관절 범위나 목표 도달 여부와 관계없이 비활성화를 요청합니다. 이전에는 `motion_status != 0`이면 요청 전에 중단했으나 이 조건을 제거했습니다. 요청 이후 새 드라이버 피드백에서 7개 모터가 모두 꺼졌는지 확인합니다. 실행 전 팔과 도구를 지지하세요.

`python nero_enable.py`도 관절 범위를 활성화의 사전 조건으로 쓰지 않습니다. 단, 실제 급정지는 자동 해제하지 않습니다. 두 명령 모두 컨트롤러가 적용하지 않거나 통신이 끊기면 성공으로 표시하지 않습니다. 이동 명령의 관절 한도와 로봇 자체의 보호 기능은 그대로입니다. 활성화만으로 범위 밖 각도나 오류 표시가 정상으로 바뀌는 것은 아닙니다.

## enable은 됐는데 NO_SOLUTION이 남아 있을 때

`NO_SOLUTION`은 컨트롤러가 요청한 위치·방향/이동 경로에 맞는 관절 구성을 계산하지 못했다는 표시입니다. 모터 전원을 켜는 enable과는 별개입니다. XYZ가 가깝더라도 방향을 유지하거나 바꾸는 조건, 관절 범위, 직선 중간 경로 때문에 실패할 수 있습니다.

2026-11-16 실제 로그에서는 다음 순서를 확인했습니다.

- `20261116_015626_a6a3c39b.jsonl`: goto의 관절 이동 다음 직선 구간에서 `NO_SOLUTION`이 발생했습니다. 직선 구간에서 위치와 방향을 함께 바꾸는 목표였습니다. 정확한 수학적 실패 조건은 로그만으로 확정할 수 없습니다.
- `20261116_015945_da7cdfc8.jsonl`: 급정지 후 reset 응답에서도 `NO_SOLUTION`이 나타났습니다.
- `20261116_031744_7c019ff1.jsonl`: enable 후 모터 7개가 False → True로 바뀌었지만 `NO_SOLUTION / MOVE_L`은 남았습니다.
- `data/nero_teach_logs/20261116_031752_77aefd5b.jsonl`: 그 상태 때문에 교시가 시작되지 않았습니다. 새로운 교시 동작에서 발생한 오류가 아닙니다.

현재 모터가 모두 켜져 있고 팔이 멈춰 있다면, 주변을 비우고 다음 명령으로 복구를 **시도**합니다.

```powershell
python nero_recover.py --execute
```

**2026-11-17 변경: 관절 목표 대신 직선(`move_l`) 목표를 보냅니다.** 실물 기록에서 `NO_SOLUTION`은 직선 명령 쪽 상태 표시로 확인됐습니다.

- 관절 이동으로는 지워지지 않았습니다. 2026-11-17 18:21 실패 직후의 홈 복귀(`move_j`)는 정상 완료됐지만 표시는 남았고, 18:29에 이전 버전(현재 관절각을 `MOVE_J` 목표로 전송)도 지우지 못했습니다.
- 새 직선 명령으로는 지워졌습니다. 2026-11-16 23:50에 관절 이동 동안 남아 있던 표시가, 이어진 직선 이동을 컨트롤러가 받아들인 지 0.5초 안에 `NORMAL`이 됐습니다.

그래서 지금은 두 단계로 시도합니다. 속도 비율은 5%입니다.

1. 현재 플랜지 위치·방향을 그대로 직선 목표로 보냅니다(움직임 없음).
2. 그래도 표시가 남으면 플랜지를 1mm 내렸다가 원래 위치로 되돌립니다(플랜지가 60mm보다 낮으면 올렸다 내립니다).

새 피드백에서 `NORMAL`이 확인되어야 복구 완료입니다. 이동·도착 확인과 급정지 처리는 다른 직선 이동과 같은 공용 함수를 씁니다. 표시가 남은 채 팔이 멈춰 있으면 급정지 없이 다음 단계로 넘어가거나 실패로 끝나고, 피드백이 끊기면 다음 목표를 보내지 않습니다. 자동 enable/disable/reset은 하지 않으며, `--execute` 없이 실행하면 상태 조회만 합니다.

`NO_SOLUTION` 표시는 이동 자체를 막지 않습니다. `nero_goto.py`와 `nero_home.py`는 표시가 남아 있어도 실행되고, `nero_goto.py`의 다음 직선 이동이 표시를 지웁니다. 이 복구가 꼭 필요한 경우는 정상 상태를 요구하는 교시 기록(`nero_teach.py record`) 전입니다. 두 단계로도 지워지지 않으면 팔을 받친 상태에서 전원을 껐다 켜는 방법이 남습니다(2026-11-16 22:50 기록에서 확인).

직선 목표로 지우는 방식은 23:50 기록 한 번과 가상 CAN 테스트로만 확인했고, 이 스크립트로 실물에서 실행한 적은 아직 없습니다.

복구 완료가 출력되면 다시 기록할 수 있습니다.

```powershell
python nero_teach.py record --duration 5 --execute
```

교시는 오류가 남아 있으면 모드를 바꾸기 전에 복구 명령을 안내합니다. 손으로 잡고 기록할 준비를 한 뒤 실행하세요.

## 전자 급정지 정책 (2026-11-16 변경)

이 SDK에서 계획된 이동을 멈추는 명령은 전자 급정지뿐이고, 급정지에서 복구하려면 팔이 처지는 reset이 필요합니다. 그래서 `nero_move_joint.py`·`nero_move_linear.py`의 공용 이동 함수(`nero_move_to.py`, `nero_goto.py`, `nero_repeat_air.py`, 교시 재생이 모두 사용)는 목표를 보낸 뒤 실패했을 때 다음과 같이 판단합니다.

| 실패 상황 | 전자 급정지 |
| --- | --- |
| 컨트롤러가 **이번 목표**를 스스로 거부(`NO_SOLUTION`, `SINGULARITY_POINT`, `TARGET_POS_EXCEEDS_LIMIT`)했고, 이후 0.5초 동안 모든 관절이 0.05도 안에서 멈춰 있음 | 보내지 않음. 모터는 켜진 채로 남고 reset 없이 다른 목표를 시도할 수 있음 |
| 컨트롤러가 거부했지만 관절이 아직 움직임, 또는 정지 확인 중 피드백이 끊김 | 요청 |
| 목표에 가까워지지 않는 시간 초과, 피드백 지연·소실, 드라이버 오류, 모터 비활성, 직선 이탈, Ctrl+C | 즉시 요청 (0.5초 관찰 없이) |

함께 바뀐 동작:

- **남아 있는 거부 표시로는 이동을 막지 않습니다.** 2026-11-16 로그에서 `NO_SOLUTION`은 급정지·reset·disable·enable을 거쳐도 남았고, 이전 코드는 이 표시만으로 모든 이동을 거부했습니다. 이제 이동 전 검사는 표시를 알리고 통과시킵니다. 모터 활성화, CAN 제어, 드라이버 오류, 관절 정지 검사는 그대로입니다.
- **옛 표시와 새 거부를 구분합니다.** 새 목표 뒤에 표시가 한 번 사라졌다가 다시 뜨면 이번 목표의 거부입니다. 표시가 계속 남은 채 2초 동안 팔이 0.05도도 움직이지 않으면 새 목표가 받아들여지지 않은 것으로 보고 급정지 없이 중단합니다. 표시가 남아 있어도 팔이 움직여 도착하면 완료로 처리합니다.
- **시간 초과는 진행 기준입니다.** `--timeout`은 전체 이동 시간이 아니라 "목표에 가까워지지 않은 채 흐른 시간"입니다. 느리지만 다가가는 이동은 중간에 끊지 않습니다.
- 진단 로그에는 `emergency_stop_requested` 또는 `emergency_stop_skipped`가 남습니다.

거부 표시는 새 직선 명령을 받으면 사라지고, 관절 명령으로는 사라지지 않습니다(2026-11-16 23:50, 2026-11-17 18:21 기록). 교시 기록은 정상 상태를 요구합니다. `NO_SOLUTION`이 남으면 위의 `nero_recover.py --execute`로 직선 목표 복구를 시도하고, 실제 NORMAL 응답 확인 후 기록하세요. 이동이 완료되어도 오류 표시가 남으면 교시 준비가 끝난 것이 아닙니다.

## 먼저 상태 조회

```powershell
python nero_read_status.py
```

| 조회 상태 | 다음 작업 |
| --- | --- |
| `CAN_CTRL`, `NORMAL`, 모터 모두 True, MOVE_J/L 등 | 작은 이동/새 교시 기록 가능 |
| `LINKAGE_TEACHING_INPUT_MODE(6)`이고 급정지 아님 | 팔을 지지하고 `control`로 복귀 |
| `EMERGENCY_STOP(1)` | `nero_reset.py`로 진단 후 조건에 맞게 복구 |
| 정상 CAN, 모터 모두 False | 필요 시 `prepare`, 이후 별도 `enable` |
| CAN/MIT이고 모터 True | 지지 후 disable → prepare → enable; 새 목표부터 보내지 않음 |
| CAN 연결 실패·피드백 없음 | 연결·전원·동일 USB-CAN을 사용하는 다른 프로그램부터 확인 |

## reset의 정확한 용도

`nero_reset.py`는 **전자 급정지 복구용**입니다. 원점 이동, 일반 오류 제거, 교시 종료 명령이 아닙니다. 옵션 없이 실행하면 조회만 합니다.

```powershell
python nero_reset.py
```

제조사는 급정지 후 모터가 활성화된 상태에서 reset이 유효하며, reset하면 모터 전원이 꺼져 팔이 즉시 처질 수 있다고 안내합니다. 따라서 팔과 도구를 받침 등으로 지지한 후에만 실행합니다.

```powershell
python nero_reset.py --execute
```

새 코드는 reset을 한 번만 보내고, **새 피드백의 급정지 해제 + 모터 7개 비활성**까지 확인해야 완료로 표시합니다. 모터가 켜진 채 오류 표시만 사라진 것은 완료로 판단하지 않습니다. 기본 확인 시간은 3초이며 `--timeout`으로 지정할 수 있습니다.

이미 정상/브레이크 미해제 상태면 reset을 보내지 않습니다. 급정지인데 모터가 비활성이라면 제조사 적용 조건과 다르다고 설명하고 자동 enable을 하지 않습니다. 이 경우에는 단순히 reset을 반복하거나 모터를 켜기보다 장비의 제조사 복구 절차를 확인해야 합니다.

복구 완료 후 이동 모드가 MIT/CPV로 남았고 모터가 모두 꺼져 있다면 아래를 한 줄씩 실행합니다.

```powershell
python nero_teach.py prepare --execute
python nero_enable.py
python nero_read_status.py
```

## 검증 범위

로그의 교시 종료 상태, 복귀 응답 누락, 모터 상태 변화, 이동 시간 초과, reset 무응답/불완전 복구는 가상 CAN으로 검증합니다. 이 테스트는 실물의 중력 보상·충돌·경로 도달 가능성을 검증하지 않습니다. 이번 읽기 전용 실물 조회는 USB-CAN 채널 0을 열지 못했으므로 실물 상태와 수정 후 물리 동작은 아직 확인하지 못했습니다. 실제 이동·모드 변경·reset 명령은 이번 점검에서 보내지 않았습니다.
